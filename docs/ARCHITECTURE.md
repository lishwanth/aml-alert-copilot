# Architecture & Design Notes

## Why this problem

Compliance teams manually investigate high volumes of AML alerts, cross-referencing structured transaction patterns against unstructured regulatory guidance and writing a documented rationale for each decision. This is slow, inconsistent across analysts, and expensive at scale — and it's a problem broadly recognized well beyond pure banking, since any payments-touching or fintech-adjacent product also cares about fraud/AML tooling.

## Why this dataset

The [IBM Transactions for Anti-Money Laundering (AML)](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml) dataset is real, published data (CDLA-Sharing-1.0 license), generated by IBM's multi-agent simulation rather than derived from or resembling any real institution's data. It ships with ground-truth "is laundering" labels, which makes it possible to train and honestly evaluate a real classifier rather than working from unlabeled or invented data. It's also the standard benchmark used in graph-neural-network AML research, since laundering activity naturally shows up as structure in the transaction graph.

**No data or patterns from any employer or client system are used anywhere in this project.**

## The config-driven client adapter (FDE-relevant design choice)

`config/clients/bank_a.yaml` and `config/clients/bank_b.yaml` map the *same* underlying real transactions to two differently-shaped export formats — different column names, same real data. The point isn't the fake bank names; it's proving that onboarding a new client's data shape is a configuration change, not a pipeline rewrite. This is deliberately the same motion a Forward Deployed Engineer does when adapting a platform to a new customer quickly, and it's meant to be discussed as such in interviews.

## Why not every step uses an LLM

An LLM is comparatively slow, expensive, and non-deterministic. Using one for every step in a data pipeline is a common but avoidable mistake in GenAI portfolio projects. This project intentionally allocates work by what's actually appropriate:

| Task | Tool | Why |
|---|---|---|
| Schema/null/range/duplicate validation | Great Expectations | Deterministic, fast, must run on every record |
| Risk scoring across the full dataset | XGBoost/LightGBM | Cheap, fast, explainable, trained on real labels |
| Graph-structure anomaly signal (stretch) | GNN (PyTorch) | This dataset is the standard benchmark for exactly this technique |
| Data-pipeline judgment calls (schema drift, quarantine decisions) | LLM ingestion agent | Genuinely ambiguous, low-volume, needs reasoning — not a per-row job |
| Investigation of flagged transactions | LangGraph multi-agent + RAG | Needs language synthesis across structured signals and unstructured regulation text — the one place an LLM is the right tool |

The LLM/agent layer only ever touches the small, pre-filtered set of transactions the ML/DL layers already flagged — never the raw dataset. That ratio (e.g., "the LLM reasoned about 0.3% of transactions; ML screened the other 99.7%") is a deliberate cost/latency argument, not an afterthought.

## Deployment: Groq for the public demo, vLLM for the architecture story

The public, click-and-try demo (linked from LinkedIn) runs its LLM calls through Groq's hosted inference API — free tier, no GPU ops, no risk of a surprise AWS bill from public traffic. Separately, vLLM is exercised on a temporary AWS GPU instance (spun up for development/benchmarking, then shut down) to get genuine hands-on serving experience and a segment for the demo video.

This split is itself a real architecture answer, not just a cost hack: a bank's actual AML data can never leave its own infrastructure to a third-party inference API, which is precisely why self-hosted vLLM is the correct choice for a real deployment, while Groq is appropriate for a public demo running on already-public synthetic-origin data.

## Evaluation

Ragas scores the investigation memos for faithfulness against the retrieved regulatory text and measures retrieval precision/recall against the RAG corpus. A custom check additionally verifies whether known labeled laundering transactions get matched to the correct typology guidance — giving a second, domain-specific correctness signal beyond the generic RAG metrics.

## What would change at real bank scale

Worth stating explicitly rather than pretending this POC is production-scale: at real volume, DuckDB would be replaced by Snowflake or Spark for the feature store, batch ingestion would become Kafka/Kinesis-based streaming, the vector index would need caching/sharding, vLLM would run as an autoscaled fleet behind a queue rather than a single instance, and every pipeline decision would need audit/lineage logging for regulatory traceability. None of this is built here — it's the answer to "what would you do differently at scale," not a gap being hidden.
